# Prototype Instructions

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

**Exception, explicitly requested by the user — do not start a new dev server.** The user runs `npm run dev` themselves in their own terminal (port 5173) and keeps it running across sessions. Never call a launch config or otherwise spawn/manage that process — only open a browser tab pointed at the existing `http://localhost:5173`. The user's server frequently isn't reachable from this environment for reasons outside either side's control (seen throughout this project's history) — if `http://localhost:5173` won't load, say so plainly and ask the user to confirm it's running, rather than starting a competing instance.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

Build app UI in `src/`. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run build` and `npm run test:sites`; the build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.

**Deploy target:** the user also deploys this independently to Vercel via the Vercel CLI (`vercel --yes` from this directory), live at `hair-by-julia.vercel.app` (and a second `hairbyjulia-prototype.vercel.app` project from earlier in the project's history — the user has used both; ask which one is current if it matters). `vercel.json` sets `outputDirectory: dist/client` since Vite's own output isn't at the Vercel default path. The user has sometimes deployed themselves between sessions — if something looks stale on Vercel, that's likely why; it's not this repo being out of sync.

## Who this is for

HairByJulia is a real hairdresser's (Julia's) booking/calendar prototype, built to demo to her as a real client and, if it lands, evolve toward something she actually uses day to day. **She is explicitly not comfortable with computers** — every design decision should default to the simplest, most obvious option a non-technical person would understand, over a more "powerful" but fiddly one. The person actually operating Claude Code in this repo is not Julia — he's building this for her and relays her feedback (sometimes as photos of her testing on a phone/tablet/laptop, sometimes as her own words translated). Demo sessions with Julia are a recurring real deadline; treat "she has a meeting tomorrow" literally.

## HairByJulia design decisions

- Warm ivory, wine/aubergine, blush, sage visual direction (`--wine`, `--rose`, `--line`, `--sage`, `--ivory` custom properties in `src/styles.css`). Playfair Display for headings/numerals, DM Sans for body, Phosphor icons throughout.
- Calendar logic operates at real 5-minute precision everywhere, even when major labels are less dense.
- A complex client visit is one coherent appointment containing hands-on and processing/open phases (see "Scheduling model" below) — this is the core pitch of the whole prototype, not a side feature.
- Parallel bookings occupy the processing/open lane; private bookings lock the whole interval (including their own downtime) from anyone else.
- Day, 3 Days, Week and Month are working calendar modes. Period arrows navigate by the active view, Today resets to the real day, clicking a day opens its detailed schedule.
- No `window.confirm`/`window.alert` — every destructive or consequential action (reset demo data, delete an appointment) gets its own small inline confirm UI in the same component, not a native browser dialog.

## Architecture

- **State**: `src/store/AppContext.jsx` — React Context + a single `useReducer`, no external state library. `useAppState()` / `useAppActions()` are the only way components read/mutate state; `useAnnounce()` dispatches a toast that auto-clears after 2.4s. Persisted to `localStorage` (`hairbyjulia-prototype-data-v2`) via a `seedDateKey` staleness stamp: on load, if the stored `seedDateKey` doesn't match today's real date, the store treats storage as stale and reseeds fresh — so the demo always looks like "today" no matter when it's opened, while same-day edits survive a refresh. `RESET_DATA` (the sidebar's "Reset demo data" link) forces this regardless of date.
- **Time**: `src/lib/format.js` exports a **live** `NOW` binding (`export let NOW`) computed via `Intl.DateTimeFormat` pinned to `Australia/Melbourne` — not the browser's local timezone, not a fixed demo date. `refreshNow()` recomputes it; `App.jsx`'s `Shell` ticks this every 30s. Any new timestamp-producing code must read the live `NOW` export, not `new Date()`, or relative-time labels ("3h ago", "Today") drift.
- **Scheduling model** (`src/lib/scheduling.js`): an appointment has `stages: [{label, durationMin, occupiesStylist}]` and a `lane: "primary" | "parallel"`. `stagesWithOffsets` annotates each stage with its absolute start minute. Key exports:
  - `findConflictingAppointment(appointments, appt, atStartMin)` — does this appointment's *hands-on* time collide with anyone else's hands-on time, or land inside a private client's full span? Returns the other appointment (for a "double-booked with ___" message) or `null`. **Never blocks anything** — the whole app's philosophy is "allow it, warn clearly" rather than refuse; Julia sometimes deliberately wants to overlap two clients for a few minutes.
  - `isSqueezedAt(appointments, appt, atStartMin)` — should this render in the parallel (side) lane? True on a real conflict *or* when it lands inside anyone's free/processing stage (a legitimate squeeze, not a clash). Only genuinely standalone time earns `"primary"`. Used by both drag-to-reschedule and the reschedule modal to re-decide the lane on every move — lane is **not** fixed at booking time, it's recomputed on every reschedule.
  - `searchAvailability(appointments, durationMin, now, opts)` — the "Pick a time" search, tags each result `overlap: {clientId, stageLabel}` when it only exists by fitting into someone else's downtime.
  - `lastAppointmentFor` — a client's most recent past appointment, used to suggest "last time this took Anna 5h" instead of a generic duration guess (hair genuinely varies per client).
- **Geometry** (`src/lib/geometry.js`): `PX_PER_HOUR = 96`. All pixel math for the day grid goes through here, driven into CSS via the `--px-per-hour` custom property — never hand-tune a pixel value in the day grid.
- **Mobile vs desktop day view**: `src/lib/useIsMobile.js` exports `useIsMobile()`, breakpoint **1250px** (not a typical phone breakpoint — the desktop grid's `minmax(720px,1fr) 275px` columns genuinely need ~995px, so anything narrower, tablets included, was broken before this existed). `DayView.jsx` is a thin wrapper picking `MobileDayAgenda.jsx` (plain chronological list, no drag, own "Reschedule"/delete controls) or `DesktopDayGrid` (the pixel-precise two-lane grid, in the same file) based on that hook. Keep both in sync when changing shared behavior (reminders, cancel/delete, reschedule, conflict badges) — they intentionally duplicate some UI because the layouts are fundamentally different, not because one was forgotten.
- **Booking flow** (`FindTimeAssistant.jsx`): three numbered steps — Who (client + service autocomplete, privacy checkbox lives in step 2 now, not step 1, since it's only meaningful once "includes processing time" is chosen), How long (quick chips + manual entry that auto-applies on blur/Enter, or the 3-stage "Includes processing time" editor), Pick a time (≤4 suggested slots, or an exact date+time pair that live-jumps the real calendar to that day and auto-applies the moment both fields are filled — no separate confirm button anywhere in this flow anymore, on principle). A persistent "Booking: {day} · {time}" summary sits directly above the "Book appointment" button — the one place that always says plainly what's about to be committed, added after a real bug where a stale list-selection got booked instead of a freshly-typed exact time.
- **Service catalog** (`src/lib/services.js`): Julia's real price list (Styling/Colour/Treatments), used for the service-field autocomplete. Prices are shown nowhere in the UI (removed after feedback) — the catalog only supplies names. Any service typed that isn't on the catalog is automatically remembered for future autocomplete by scanning past `appointments` for unrecognized `serviceLabel`s (see `customServices` in `FindTimeAssistant.jsx`) — no separate persisted "custom services" list, it just reads data that already persists.
- **Reschedule** (`RescheduleModal.jsx`, opened via `actions.openReschedule(id)`/`ui.reschedulingAppointmentId`): a small modal for moving an *existing* appointment to a different day/time (drag only works within the currently-visible day, so this covers "client calls weeks out to move it"). Typing a date live-navigates the real calendar underneath (the modal only dims it at 34% opacity) so Julia sees the actual day, not a re-derived summary; backing out without saving reverts the calendar to wherever it was. Recomputes lane via `isSqueezedAt` on save, same as drag.
- **Find a client** (`ClientSearchModal.jsx`, triggered from `TopBar.jsx`): search by name, see their upcoming (not past) appointments with date/time, click one to jump straight to that day with the card scroll-highlighted.
- **Delete vs cancel**: `CANCEL_APPOINTMENT` marks `status:"cancelled"` (stays visible, strikethrough, Restore button). `DELETE_APPOINTMENT` (new) actually removes it from the array — only offered on already-cancelled appointments, behind an inline "Remove for good? [Yes, remove] [Cancel]" confirm, never a native dialog.
- **Visit amounts**: `client.visits[]` entries can carry `amount`/`method` (cash/card), edited alongside the formula in `ClientProfilePanel.jsx`'s visit editor, shown in visit history. **Deliberately not wired into the Finance page's transactions** yet — that would need de-duplication logic (editing a visit's amount again shouldn't double-count) that wasn't built; ask before adding it if requested again.

## Known CSS traps in this codebase (read before touching `styles.css`)

- **Bare legacy class names collide silently.** The file still carries several *dead* rules with plain, unqualified selectors from the very original hardcoded mockup — `.private{...}`, `.cancelled{...}`, `.proposed{...}`, `.anna{...}`, `.vasya{...}`, `.olivia{...}`, `.a1{...}`, `.a2{...}`, `.availability{...}` (a real duplicate — one legacy, one live) and similar. A new component using any of these exact words as a class name (even combined with other classes) will silently inherit old absolute-positioning/layout rules and visually break in confusing ways. This has bitten real work twice already (`AppointmentCard`'s multi-phase controls, `MobileDayAgenda`'s status classes). **Always prefix new state classes** (`agenda-private`, not `private`) or grep for the bare name first.
- **`min-width:auto` flex/grid overflow.** A flex or grid item containing `white-space:nowrap` + `text-overflow:ellipsis` text (or a native `<input>`) won't actually shrink below its content's intrinsic width unless the item itself has `min-width:0` (not just its child) — bit `.conversation-row` and the exact-time-row's native date/time inputs. Any new row/card with an ellipsis-truncated child inside a flex/grid needs `min-width:0` on the flex/grid item itself.
- **Absolutely-positioned corner elements collide.** `.booking-controls` (reminder/reschedule/cancel chips) and `.booking-title-overlay`'s time badge both want the same top-right corner on multi-phase cards; the same happened again on simple cards between the controls and the centered name/time text. Any new absolutely-positioned overlay in a `.booking` needs to explicitly account for what else occupies that corner (`showControls`), not just its own layout.
- **`position:sticky` isn't portable across containers.** A sticky element's behavior depends on which ancestor is actually scrolling. `.chip-btn.restore`'s `position:absolute;top:50%` and `.assistant-footer`'s `position:sticky;bottom:-21px` were both tuned for one specific container and broke (overlapping other content, or "sticking" immediately instead of near the scroll boundary) when reused inside a differently-structured parent (the mobile agenda list, the full-screen mobile assistant). When reusing a component's classes in a new structural context, re-derive the positioning rather than assuming it travels.
- The mobile breakpoint constant lives in **two places that must stay in sync**: `src/lib/useIsMobile.js` (`BREAKPOINT`, JS) and the `@media(max-width:...)` in `src/styles.css` (CSS). Currently both `1250`.

## Verification workflow used throughout this project

- The user's own `npm run dev` is the only server; this environment's Bash `netstat` check and the browser tool's `navigate` frequently disagree on whether it's reachable, and it goes up and down between messages for reasons outside this session's control. Don't assume either signal is authoritative — just try `navigate`, and if it fails, say so plainly and ask the user to confirm the server's running, rather than guessing or starting a new one.
- Programmatically dispatching synthetic DOM events (`el.dispatchEvent(new PointerEvent(...))`) from `javascript_tool` is unreliable for drag/pointer interactions in this environment and can produce false negatives that look like app bugs but aren't (discovered and re-confirmed twice). The reliable pattern for testing drag/pointer logic without a real mouse: grab the React fiber's props directly off the DOM node (`el[Object.keys(el).find(k=>k.startsWith('__reactProps'))]`) and call the handler functions (`onPointerDown`/`onPointerMove`/`onPointerUp`) directly with plain object "fake events" (`{clientY, button:0, currentTarget: el, stopPropagation(){}, ...}`). This bypasses the browser's synthetic-event quirks entirely and has reliably caught real bugs (a stale-closure race in the drag-commit logic) that DOM-event dispatch missed.
- State updates from a *separate* `javascript_exec` tool call are reliably committed by the time of the *next* tool call; state read back within the *same* synchronous script block right after a state-setter call is not (React hasn't flushed yet) — this produced a false "nothing happened" reading more than once. Split "act" and "verify" into separate tool calls when checking React state after an interaction.
- `computer{action:"screenshot"}` and pixel-`coordinate`-based `computer` actions require the Browser pane to actually be composited/displayed to the user; in a session where it isn't, these fail outright ("not compositing frames") while `ref`-based clicks, `read_page`, and `get_page_text` keep working fine. Prefer `read_page`/`get_page_text`/`javascript_tool` for verification; fall back to `ref`-based `computer` clicks for interaction; only rely on screenshots when they're confirmed working in that session.
- Always test a code change in a **freshly-created tab** (`tabs_create` then `navigate`), not a reused one — Vite HMR can leave a reused tab in a stale module state that throws spurious errors (e.g. `useAppState must be used within AppProvider`) unrelated to the actual change.
- After any live test that adds/moves/cancels a seed appointment, use the sidebar's "Reset demo data" (or, on mobile where that control is hidden, `localStorage.clear()` + reload) to restore the clean demo state before ending the turn — never leave test data in what the user might use for a real demo.
